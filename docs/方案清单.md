# 长堤风貌街 AI 智慧导览小程序 · 方案清单

> 依据：《08 基于LBS与文旅知识图谱的AI智慧导览小程序研发》需求登记表、《问题与对应方案》、模块 1–6 说明。
> 主展示端：**竖屏手机微信小程序**。后台管理端、算法服务只列支撑项，不做游客端页面。
> 优先级：**P0** 预赛演示必须有 ｜ **P1** 正式版必须有（对应考核指标） ｜ **P2** 探索/加分项。

## 一、问题 → 方案 → 小程序落点

| # | 企业提出的问题 | 我们的方案 | 小程序里在哪儿体现 |
|---|---|---|---|
| 1 | 内容单一，缺少个性化游览引导 | 多触发方式导览（地图点击 / 扫码·NFC / LBS 到达 / 拍照识别）+ 三条候选路线 | 首页四个识别入口、路线规划向导、三路线对比页、游览进行页 |
| 2 | 讲解供给不足，人工难调度 | AI 语音讲解打底（普通话/英语/粤语先行），真人讲解员在线预约、改约、评价 | 点位详情的讲解播放、全局迷你播放条、讲解员匹配与预约流程 |
| 3 | 文化资源孤立，缺少故事与互动 | 知识图谱「建筑—人物—事件」关联、故事线、像素微缩地图、打卡点亮与电子小卡 | 点位详情的关联卡片、图谱探索页、故事线页、像素地图、卡册 |
| 4 | 停车无前置预测，与路线脱节 | 周边停车场比较、按出行偏好推荐、未来 1 小时余位预测、停车场作为路线起点 | 路线向导「自驾」分支、停车比较页、停车场详情预测曲线 |
| 5 | 数据口径不一，反馈无法追踪评估 | 统一 point_id 数据底座、匿名诉求「提交—分派—处理—反馈—评价」、全链路埋点 | 诉求提交与追踪页、处理人员工作台、各页面埋点 |

## 二、小程序信息架构（竖屏）

```
底部 Tab（4 个，与效果图一致）
├── 首页      识别入口 / 开始规划 / 继续游览 / 推荐点位 / 故事线 / 停车速览
├── 导览      真实地图 ⇄ 像素地图 / 分类筛选 / 点位抽屉 / 游览进行中
├── 服务      讲解员预约 / 停车 / 诉求反馈 / 任务奖励
└── 我的      卡册与点亮进度 / 我的路线 / 我的预约 / 我的诉求 / 设置 / 角色工作台

全局常驻
├── 迷你播放条：讲解播放中时悬浮在 Tab 栏上方，点开进入全屏播放器
└── 外部直达：扫二维码 / 碰 NFC → 直接打开对应点位详情并完成打卡
```

**分包建议**（保证首屏 ≤ 2s）：主包只放首页、地图、点位详情、播放器；图谱、故事线、像素地图、讲解员预约、停车、诉求、卡册各自分包，首页空闲时预下载。

## 四、竖屏交互与体验规范

- [ ] **设计基准**：750rpx 宽，按 375×812 出稿；处理顶部胶囊按钮与底部安全区。
- [ ] **单手操作**：主操作按钮放在屏幕下半部；地图页靠底部抽屉承载内容，不用顶部弹窗。
- [ ] **全局迷你播放条**：在 Tab 栏上方常驻，切页不断播；讲解音频可缓存，弱网可播。
- [ ] **定位与权限**：首次进入只说明用途，不强制授权；拒绝定位时降级为「地图点击 + 扫码」也能完整使用。到达检测需要连续定位，app.json 里声明对应的隐私接口并配置用户隐私保护指引。
- [ ] **坐标**：数据按 CGCS2000 提供，小程序地图使用 GCJ-02，入库时统一转换，不在前端临时转换。
- [ ] **多语言**：界面文案与讲解内容分开管理；首次进入读取系统语言，自动选界面语言与讲解员语种。
- [ ] **性能**：首屏 ≤ 2s，关键页面响应 ≤ 1.5s，路线生成 ≤ 3s（超时显示骨架屏和进度文案）。
- [ ] **数据真实性标识**：示范或模拟数据（停车余位、讲解员）在页面上明确标注「示范数据」。
- [ ] **视觉方向**：效果图采用蓝白科技风；像素地图单独成一种风格，作为「探索 / 收集」模式，与日常导览界面区分。

## 六、指标与埋点对照

| 指标 | 目标 | 需要在哪儿埋点 |
|---|---|---|
| 语义关联推荐 CTR | ≥ 25% | P08「与这里有关」、P11 图谱卡片的曝光与点击 |
| 路线采纳率 | ≥ 40% | P03 生成 → 采纳 → P07 完成 |
| 讲解 MOS | ≥ 3.8 | P09 播放结束后的 5 分制评分（抽样弹出） |
| 讲解词与点位匹配准确率 | ≥ 90% | 后台人工抽检 + P09「讲的不是这里」反馈按钮 |
| 讲解员在线预约使用率 | ≥ 30% | P17 线上预约量 / 总预约量（需运营方提供线下量） |
| 平均预约确认时长 | ≤ 30 分钟 | 预约提交时间 → 讲解员确认时间 |
| 车位预测 MAE | ≤ 20% | 后台：预测值与实际余位比对 |
| 错峰建议采纳率 | ≥ 25% | P20 推荐曝光 → 选择推荐停车场 / 设为起点 |
| 首屏 / 关键页面响应 | ≤ 2s / ≤ 1.5s | 小程序性能监控，取 P95 |
| 可用率 | ≥ 99.5% | 后端服务监控 |

## 七、开工前需要和需求方确认的问题

1. **小程序形态**：独立小程序，还是继续嵌入「乐游蓬江」？这决定登录、支付、订阅消息和 NFC 拉起能力能不能用。
2. **数据交付时间**：五类数据（点位、史料、讲解员、停车与客流、游客行为）什么时候给、格式是否按需求书。
3. **二维码 / NFC 布设**：哪些建筑和文物允许贴码，由谁审批、谁施工。
4. **停车数据源**：有没有实时余位接口和历史进出场记录；有没有可用的摄像头画面。
5. **讲解员**：真实人数、语种、排班方式；预约由讲解员本人确认还是由管理方统一分派。
6. **讲解内容审核**：史实审核由哪个单位负责，审核周期多长。
7. **奖励**：礼品或消费券由谁出、数量多少、怎么核销。
8. **诉求平台**：对接哪些处理部门，现场人员是否愿意用小程序工作台。

## 八、预赛演示（P0）最小闭环

按演示顺序：

1. 首页 → 规划向导选「侨乡历史 + 60 分钟 + 自驾」
2. 三条候选路线对比 → 采纳「侨乡人物线」（首站为停车场）
3. 停车比较页显示余位与推荐理由 → 设为起点
4. 游览进行中 → 到达旧海关大楼（扫码或手动）→ 自动打卡
5. 点位详情 → 播放 AI 讲解（普通话 → 切换粤语 / 英语）→ 查看关联人物与事件
6. 打开故事线 → 跳到下一个关联点位
7. 预约真人讲解员 → 提交 → 我的预约显示待确认
8. 我的 → 卡册新增一张小卡，像素地图点亮一栋建筑

所需数据：10–15 个真实点位、1 条人工整理的故事线、5–8 个可点亮的像素建筑、3 种语言的讲解音频、3–5 个示例讲解员、2–3 个停车场的示范数据。
