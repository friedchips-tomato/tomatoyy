# 乐游蓬江 AI 智慧导览小程序 · 项目技术方案

**应用场景**　江门长堤风貌街智慧导览

**申报依据**　桌面 2026-11-23 版揭榜书、企业需求登记表和六模块研发材料

## 一、项目背景与需求分析

长堤风貌街的一期平台已经提供点位、历史建筑、讲解员和停车场的展示及查询能力。企业提出在既有入口上发展面向街区实地游览的服务，让游客在出发前能安排交通和行程，在到达后能发现与当前位置相关的文化内容，并能按需要获得自助或人工讲解。对街区而言，智慧文旅建设还要让原本分散在不同单位的文化资料、运营信息和反馈记录能被持续维护，并用于复盘服务效果。场景和一期情况见 `D:/乐游蓬江AI智慧导览小程序/资料解读/08 基于LBS与文旅知识图谱的AI智慧导览小程序研发.txt`。

| 企业提出的问题 | 对游客与运营造成的影响 | 本项目的响应 |
|---|---|---|
| 内容呈现单一，缺少个性化引导 | 游客逐页浏览静态图文，难以依据位置、兴趣及可用时间决定先去哪、途中怎么调整 | 将统一点位目录连接地图、候选路线、到站提示与讲解，让游客按自身偏好选择行程 |
| 人工讲解供给不足、调度困难 | 语种、时段和服务范围难以同时匹配，预约靠线下沟通，旺淡季资源分布难以量化 | 为常见点位提供多语种基础讲解，人工讲解承接深度游览，逐步接通排班、预约、确认、改约和评价 |
| 文化资源相互孤立 | 建筑、人物、事件与非遗各自陈列，游客难以从一个点追溯其来历或发现下一个相关地点 | 建立可回查来源的实体关系，从地理浏览衔接到主题故事及关联点位探索 |
| 停车缺乏提前引导 | 仅看当前余位难以判断到达时情况，点满后绕行，停车处与步行游览衔接弱 | 展示车场位置、信息时间和备选方案，取得运营数据后验证短时预测，并把所选停车场纳入去程及返程路线 |
| 数据口径分散、反馈难追踪 | 内容、车位及排班更新频率不同，服务体验缺少可复算的记录 | 统一数据字典、来源、版本和维护职责，结合脱敏业务埋点与接诉即办的受理、办理、评价记录 |

问题与对应方案同时见 `D:/乐游蓬江AI智慧导览小程序/资料解读/问题与对应方案_当前.txt` 和 `docs/方案清单.md`。

游客端优先满足外地首次到访、自驾、步行或公共交通到访，以及有明确文化兴趣或语种需求的游客。首次到访者需要清楚的入口、点位介绍和易理解的推荐理由。本地回访者需要不同主题、可自由跳站的探索方式。自驾游客需要在到达前比较车场，停车后还能接续游览和安排取车。非自驾游客需要明确可通行的步行段和接驳条件。对于愿意深入了解历史或需要小团讲解的游客，系统提供真实可预约时段和状态查询。运营人员需要有来源的文化资料、可更新的开闭状态、预约记录、反馈流程及可复算的统计。讲解员需要明确的服务地点、语种、排班与处理待确认预约的入口。发榜方参与数据提供、业务核验和试点协调，揭榜方承担研发、集成、测试及交付，分工以桌面揭榜书为准。

## 二、建设目标与研究目标

企业登记表“核心指标与交付物”依次列出六组业务与性能指标及一组交付要求，另列申请软件著作权。以下沿用前七项的顺序，将软件著作权并入交付管理；每项正式阈值、当前证据与验证缺口集中列在第九节。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/08 基于LBS与文旅知识图谱的AI智慧导览小程序研发.txt` 的 P36–P44。

1. **组织可追溯的文旅知识。** 围绕建筑、人物、事件、文化资源和商业业态开展抽取、归并和关系审核，考察去重后的点位覆盖与实际语义推荐点击，研究如何让游客顺着真实关系继续探索，并追溯每一段历史叙事的依据。
2. **让推荐路线能被走完。** 基础路线先用可达道路、兴趣、时长与开放约束生成，再研究天气、人流、文化关联、停车与返程等条件下的重算。用服务耗时及游客按推荐路线游览并完成的比例评价效果。
3. **提供可信、可听的多语种讲解。** 通过点位检索、生成、审校和语音输出建立内容流程，按点位匹配、听感及语种范围验收。游客可按需要选择语言和播放时机。
4. **让真人讲解服务可预约、可确认。** 研究语种、服务区域和时段约束下的匹配方法，形成真实排班与预约状态记录，用线上使用率和确认时长评价业务运行。
5. **研究可解释的停车预测和错峰引导。** 先建立时序预测及回测基线，再以授权运营数据检验未来一小时误差；用能核验的到达证据评估建议采纳，按实际到达时段衔接车场与游览路线。
6. **检验小程序运行性能。** 在约定终端、网络及观测窗口下评价首屏、关键页面响应及核心功能可用率，保留冷启动、关键请求和运行监测记录。
7. **形成可部署及可交接成果。** 交付前后端部署包、图谱结构与数据、讲解语料、算法接口、测试报告与运营手册，配合软件著作权申请及教学移交。最终成果以揭榜书表 3 和登记表提交要求共同核验。

## 三、系统总体技术架构

路径以仓库根目录为基准。编写本册的工作树保留 `prototype/`、`prototype-paper/` 和 `docs/`，停车及接诉即办目录已在 `D:/乐游蓬江AI智慧导览小程序/tomatoyy` 的 `feature/intake-public-submission` 集成检出中核对，证据版本为 `ebc0a82617dd0bb0a357a6c79fcc95df9333f9ed`。下图中的相关路径按该集成检出解析，带分支名的算法路径按对应 Git 分支解析。图中同时列出现有落点与后续集成位置。

```text
应用端          prototype/、prototype-paper/（导览 H5、运营台）
                changdi-intake/miniprogram/（接诉即办微信端）
                │ 地图点选、路线选择、内容播放、停车与诉求
                ▼
服务接入        changdi-intake/guide-bridge/（导览侧接入与转发）
                changdi-intake/server/（工单、行为事件、停车示范接口）
                changdi-intake/docs/openapi.yaml（已公开的接入契约）
                │ 按点位或业务 ID 调用，准备受控数据和结果
                ▼
算法            parking-forecast/（训练、回测、运行时，集成检出）
                route-recommender/（algo/route-recommender）
                guide-match-profile/（algo/guide-match-profile）
                │ 地理与业务约束、图谱关联及可审核文案
                ▼
图谱与检索      kg-recommend/（algo/kg-recommend，未合并）
                讲解史料检索和正式图谱服务待集成
                │ point_id、graph_id、history_id、guide_id
                ▼
数据底座        prototype-paper/data/points.js（导览演示内容）
                changdi-intake/server/migrations/（工单与脱敏行为存储）
                parking-forecast/data/synthetic/（停车合成时序）
                五类业务数据和增量更新机制待接入
```

数据底座先将名称、别名、坐标与坐标系、开放状态、来源和审批记录与稳定的 `point_id` 关联。应用端根据点位映射访问详情和语料，图谱用实体关系表达文化联系，路线端以同一目录读取位置、服务状态和约束。示意底图热点与导航坐标各有字段，应用渲染可以调整，点位主键仍可被史料引用、打卡记录和验收样本追溯。真实业务目录导入时要核对 H5 演示编号、图谱样例编号和正式编号间的映射，防止把字符串恰好相同的记录当作同一实体。

服务层分别处理公众查询、业务授权和演示数据来源。游客从导览侧进入诉求服务后可凭回执查询脱敏进度，发布反馈、查阅联系方式及补办办理要依照角色与授权。供统计使用的事件按 `demo` 和 `operational` 识别，记录出处及覆盖区间，统计端可以明确指出不可得的指标。工单历史状态以事件回放核对，当前状态仅用于当前办理。具体读写和停车接口见 `changdi-intake/server/README.md`、`changdi-intake/docs/openapi.yaml`，导览接入服务见 `changdi-intake/guide-bridge/`。

应用层延续竖屏地图和点位交互，通过脚本及截图验证样板流程。正式导览的微信定位、扫码、发布权限、网络条件与现场体验需要在获准的环境中复验。接诉即办与导览有各自的业务记录和权限边界，统一的是用户可抵达的入口、可追溯的业务事件和必要的运营汇总。前端收到缺失、陈旧或源为合成的停车结果时，明确标出状态并保留可用的基础信息。

## 四、六模块技术实现思路

### LBS 导览与个性化路线

**现状。** `prototype-paper/data/points.js` 登记 10 个示意点位和 3 条预设候选路线，`prototype-paper/app.js` 与 `prototype-paper/screenshots/h5/` 留有选点、路线预览、游览进度和完成回顾的 H5 证据。点位名称和值得核对的实地锚点已经整理，热点和相对方位属于演示。路线研究代码在 `algo/route-recommender` 的 `route-recommender/`，该分支的本地评测独立于 H5 预设路线和微信场景。

**技术方案。** 游客先主动输入主题、时间、步行强度、意向地点及出行方式。生成器按开放时段和可通行道路缩小候选集，综合兴趣匹配、行走距离和停留时间形成可比较的候选路线，返回点位顺序、预计总时长、步行距离及推荐理由。基础版支持换下一站，进阶版同时考虑道路、客流和天气，在停留超时、道路受限、停车场变更时用已完成点位与剩余时间重算。自驾路线保留停车起点与返程取车，步行与公共交通接驳根据真实道路和可用条件安排。可行解不足时说明约束，保留已经计算出的选择。游览状态要区分浏览、提醒到达、确认打卡和完成路线，便于恢复进度与核算实际完成。现场可从地图、扫码及获准的 NFC 入口定位相同内容，定位被拒绝或精度不足时保留手选和阅读功能。

**数据依赖与指标。** 需要核验的坐标、可通行道路、开放时段、交通限制、游客主动偏好，以及条件具备时的停车、客流和天气数据。路线生成时间按揭榜书看 P95，正式采纳按获得推荐后实际按路线游览并完成的人数计。样例耗时、候选预览和点击“出发”分别只能证明算法或交互的一段。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块1-LBS.txt`、`docs/长堤导览-从样板到上线总清单.md`。

### 文旅知识图谱

**现状。** 主线尚无图谱数据文件。图谱 Schema 和样例分别位于未合并分支 `algo/kg-recommend` 的 `kg-recommend/schemas/kg.schema.json` 与 `kg-recommend/data/kg_sample.json`。样例为示意、未经核实，为模型输入输出和校验流程提供夹具。H5 中的 1 条故事线位于 `prototype-paper/data/points.js`，可演示主题叙事，正式图谱覆盖需另依已审核实体关系核算。

**技术方案。** 以点位为入口，将历史建筑、人物、事件、非遗及商业业态整理为实体，用“参与”“发生于”“位于”等有方向的关系登记实际史料支持的事实。保留来源编号、原文凭据、别名和年代；存在冲突的说法保留出处和核验状态，经审核形成公众可见的版本。对同名建筑或曾用地名，结合地点、时期和资料进行归并。算法分支已能以图结构、主题重合及路径强度提供关联推荐和理由，可生成故事骨架，再核对转场用到的关系及年代顺序。正式服务按点位查询相关实体与可信来源，前端通过逐项展开讲清关系。已有人工整理故事线按来源逐段复核，后续生成结果也按同样流程验收。

**数据依赖与指标。** 需获得建筑名录、文化普查、可靠的地方史与口述史、已授权讲解资料，并将出处登记到关系层。按发榜方清单、可靠实体关系和稳定点位 ID 去重计数，语义推荐点击率按真实推荐点击和曝光计，故事线逐条核验来源。分支里的点击代理数据按合成结果使用。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块2文旅知识图谱.txt`、`algo/kg-recommend` 的 `kg-recommend/README.md` 和 `kg-recommend/metrics.json`。

### AI 多语种讲解

**现状。** `prototype-paper/data/points.js` 有 9 篇点位三语讲解稿，提供普通话、英语和粤语文案。H5 能切换语种及使用浏览器语音能力演示播放，见 `prototype-paper/app.js`、`prototype-paper/screenshots/h5/`。当前可核对的是语料和演示链路，正式 TTS 服务、上线音频、游客听感与逐点匹配准确率单独核验。

**技术方案。** 游客先通过地图、现场二维码或有定位授权时的到达提示取得点位 ID。按点位 ID 调取经审校的史料及关联关系，给生成端提供内容范围和出处，分出短版、标准版与深度讲解。生成稿经史实审核、语种校对、地名人名复查后发布，语料、音频与点位版本同时留档。用 TTS 输出可复用音频并保留模型或服务的版本、音色和使用许可，支持播放、暂停与继续。对可能错认的建筑先让游客核对，音频加载失败保留文字。问答基于同一史料库，涉及无依据的历史判断时提示待核实。位置、朝向与停留仅用于选择适合的已审核内容或作为生成输入的场景条件。

**数据依赖与指标。** 依赖按点位归档的真实史料、发榜方审核协作、三语审校，以及具备对应语种、合法使用和合规部署条件的 TTS。语种按实际可播放、已审核产物验证；MOS 取参评游客主观评分均值；点位匹配准确率需按点位和语种抽样并保留错配记录。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块3智能语音讲解.txt`、`docs/长堤导览-从样板到上线总清单.md` 与揭榜书表 3。

### 讲解员匹配与预约

**现状。** H5 的示范人员、可选时段及本地预约记录见 `prototype-paper/data/points.js`、`prototype-paper/app.js` 和 `prototype-paper/ops.js`。独立分支 `algo/guide-match-profile` 的 `guide-match-profile/README.md` 描述了使用合成资料、评价和行为的匹配、服务能力画像及冲突场景评估。当前可核验流程和排序方法的示范，真实预约量及确认记录还待运营接入。

**技术方案。** 手机语言用于预选，游客可手动修改；按服务区域、语种和可约时段筛选后，再依据评级、服务主题与已审核的评价排序。无匹配人员时显示可选时段，并保留自助讲解入口。预约记录保留提交、确认、变更与完成事件；确认或改约时应校验同一时段剩余容量并处理并发冲突，保证重复点击和断线重试不会重复占用。评价与真实完成服务关联，运营方按排班、服务次数和评价了解资源供给，再结合旺淡季安排调度。示范记录与运营预约各自独立，后者要有发榜方或景区的实际排班和确认责任人。

**数据依赖与指标。** 接入经授权人员目录、语言、评级、服务范围、可约时段、线上与线下预约、状态时间和评价。使用率的总预约分母由运营方确认，确认时长取实际提交到确认的经过时间；将未确认、取消、改约分别留痕，保留排除依据。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块4讲解员匹配及预约.txt`、`docs/方案清单.md`。

### 停车预测与错峰引导

**现状。** 集成检出的 `parking-forecast/` 提供 Schema、合成时序、训练、回测及 JavaScript 运行时，`parking-forecast/artifacts/report.md` 和 `parking-forecast/artifacts/metrics.json` 留有模型与基线对照。后端目录、推荐和单车场预测接口见 `changdi-intake/docs/openapi.yaml`，`prototype-paper/` 可演示停车比较及选址联动。`parking-forecast/artifacts/metrics.json` 中 `source=synthetic`，`synthetic_disclaimer` 原文如下。

> 本结果基于合成数据（source=synthetic），仅证明管线可用，不代表模型精度。正式精度指标必须由真实历史数据与现场校验得出。

**技术方案。** 从车场目录、总泊位、余位观测及时间信号建立可追溯的历史序列。现有模型用增量岭回归预测相对最近可用观测的变化量，训练、验证、测试按时间分开，并检查未来观测是否意外流入特征。回测比较最后已知余位、同时间段统计和同星期统计等基线，并按预测提前量、工作日及数据质量等分层统计。真实数据接入后，记录实际的采样时间与进入系统的时间，避免把回看时已获得的信息当作请求当时可知。推理缺少必要数据时，根据条件降级到统计基线、最后观测或不可用；无数据时标注不可用，不把空值描述成满位。

游客选择目的地和预计到达时间后，根据余位、空闲率、收费、通行及后续步行距离比较停车场。按省时或少走等偏好说明首选、备选和排除理由。使用者在选择车场后可接续步行路线，自驾返程仍能回到停车场入口。缺路网时，回测报告说明总时间使用近似估计；缺接驳点时，接驳方案不可行。商业活动、客流和天气信号是否能稳定提供需先核验，整理到同一观测时间轴再开展对照。现场有授权接口或经许可并可看清泊位的摄像画面时，才研究补充采集。

**数据依赖与指标。** 必需车场目录、分时余位及可信的实际余位对照，持续补充进出场、天气、节假日和活动等。绝对 MAE 以车位计，百分比目标的归一化分母和时间范围由需求方书面确认。当前回测采用 WAPE 作为展示口径，另列绝对误差及候选归一化结果。错峰建议采纳应关联建议、游客选择和可核验的到达，导航点击与提醒曝光也单独留痕。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块5-停车.txt`、`parking-forecast/README.md`、`parking-forecast/artifacts/report.md`。

## 五、AI 大模型、知识图谱、地图定位等技术应用与边界

讲解生成服务接收点位、语种和场景输入，检索经授权的史料及可用图谱关系，生成结果随来源和版本一起审校。史实规则可查实体是否存在、引文是否登记、年代是否自洽，地方文化解释与用词仍需人工复核。生僻字、旧地名和多语种表达经校对后再合成。正式语音与模型服务需记录版本和许可，并按企业登记表准备离线或专有云部署条件。现场暂不可用时可从已审核的讲解文本或音频提供基础服务。

示意地图负责文化探索和点位交互，导航使用有合规来源的地理数据与可通行道路。GPS 的到达提示受定位精度、建筑遮挡、河岸及相邻点位影响，正式方案结合点位范围、停留、去重及用户确认判断到站或打卡。二维码、NFC 和图像识别复用点位 ID，布设、识别样本与实际可用范围分别核验。像素或纸质地图中的交互热区仍用于视觉坐标，合规坐标、现场入口与导航记录由数据底座追溯。依据 `docs/像素地图方案清单.md`、`docs/长堤导览-从样板到上线总清单.md`。

停车模型消费的是时序观测。摄像头画面在有授权、画质和视角达到采集要求时，可作为余位来源之一；若做泊位级占用，需要核对车辆与各泊位区域的对应关系，并验证遮挡时的有效性。若只有平台余位及历史记录，按可获得的结构化时序做数据治理和预测。应先核实时刻、口径和现场对照，再评价准确性。依据 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块5-停车.txt`。

## 六、数据来源与处理方式

企业要求五类业务数据由需求方提供，具体字段、交接方式、许可和频率在立项后确认。以下更新动作是建议的维护触发条件，责任人是对接占位。数据字典指向 `docs/数据字典-v0.1.md`，其归档由数据字典任务负责，本工作树交付时以该任务实际合入情况核对。五类及格式依据登记表 P53–P60、`D:/乐游蓬江AI智慧导览小程序/资料解读/模块6-基础数据.txt`。

结构化交付采用 CSV 或 JSON、UTF-8 编码。企业登记表要求经纬度统一采用 CGCS2000，时区用北京时间 UTC+8。原始坐标的来源和坐标系一并登记，按合规地图服务要求形成转换记录，供导入与实地验收追溯。素材保留原始文件和索引，登记内容版本、权利人和可用范围。处理时先接收样例并核验缺失、重复、值域、关联键和时间戳，再导入验证环境。运营源、公开核实底稿、合成夹具各保留来源字段与版本，避免覆盖真实来源。游客行为应使用目的所需的脱敏标识和受限目录，权限外的个人信息、原图和细粒度位置不进入公开输出。

运营事件应保留能复算统计的来源及状态。接口配置目前支持按事件类型声明期间覆盖，演示与运营数据可以分别汇总。覆盖缺失或不完整时先保留缺口，减少把未知记录写成零的风险。正式数据接收后需按数据字典比对口径，补齐试点期间的计数范围与异常处理说明。相关契约见 `changdi-intake/docs/openapi.yaml` 和 `changdi-intake/server/README.md` 的“导览来源与行为上报”“内部月报”。

## 七、项目创新点与可行性分析

**从读点位简介到沿文化关系游览。** 点位目录把地图上的建筑与史料、人物、事件和可播放讲解连接起来。游客阅读建筑详情后，可以继续查看相关事件和下一处点位；运营人员能回查关系和文案源头，发现事实有分歧时及时修订。研发重点是多源材料归并、关系来源追溯与故事转场的一致性校验。图谱分支已有样例、结构和推荐算法，可以在拿到已审核资料后用同一流程检验真实关系。可行性取决于史料质量、来源权利和持续审核安排。依据 `algo/kg-recommend` 的 `kg-recommend/README.md` 和 `D:/乐游蓬江AI智慧导览小程序/资料解读/模块2文旅知识图谱.txt`。

**从选景点到可执行的时间与空间规划。** 路线同时考虑兴趣、道路、开放、停留时间及出行方式，给出为什么推荐。在具备真实时序数据后，将到达时车位可用性用于车场比较，选中车场后接续游览，并能安排返回停车起点。H5 展示游客比较候选路线的过程，独立路线分支验证算法约束，停车模块验证训练、推理及缺数据降级。现场还要检验雨天、临时封路、入口变动等条件。依据 `docs/长堤导览-从样板到上线总清单.md`、`parking-forecast/README.md`。

**让位置触发与地方文化内容在同一流程里发生。** 游客通过地图和实景锚点浏览，根据授权定位、扫码或现场凭证确认行程，按需要收听三语讲解或进入人工预约。像素风建筑、打卡点亮及收藏卡用于承载点位故事，浏览、核实到达及领卡各有状态。后续是否开展拍照识别、礼品或线下盖章联动，由素材、设备条件及运营合作共同决定。先验证一段连贯交互，再扩展街区内容，减少资料变更时的整图返工。依据 `docs/像素地图方案清单.md`、`docs/长堤导览-从样板到上线总清单.md`。

**用有来源的事件连接服务与运营评估。** 导览、预约与停车使用脱敏事件保留运营反馈，工单通过公开脱敏查询与授权办理实现追踪。运营台可复核原始状态变化，分析侧按来源及覆盖区间复算，见 `changdi-intake/server/README.md`。项目积累的数据字典、接口、分支算法和测试用例可以整理成课程实验、毕设选题和跨学科实践任务。迁移到其他街区时需重新核验当地史料、道路、语种、许可和运营流程。

**榜单计算口径。** CTR 为被点击的推荐条目数除以曝光条目数。路线采纳率为按推荐路线游览并完成的游客数除以获得推荐路线的游客数。MOS 是参评游客主观评分均值，采用 5 分制。绝对 MAE 为预测余位与实际余位差的绝对值均值，单位为车位。纳入评分前需确认百分比归一化和时间范围。响应时延从请求至结果返回，取 P95。实测保留分子、分母、样本范围、失败与排除记录，分母为零时按共同确认规则处理。登记表 P72 的公式如下。

    Score_main = 100 × [0.25 × CTR + 0.25 × AdoptRate + 0.2 × (MOS / 5)
                 + 0.2 × (1 − min(MAE / 20%, 1)) + 0.1 × (1 − min(T_resp / 3s, 1))]
    最低记为 0 分。

**本地工程证据。** 集成检出的运行回归共通过 414 例，小程序 253、后端 140、导览接入层 21，入口分别见 `changdi-intake/miniprogram/package.json`、`changdi-intake/server/package.json`、`changdi-intake/guide-bridge/package.json` 的测试脚本。运行 `prototype/check.mjs` 和 `prototype-paper/check.mjs`，两套自检均为 0 错误、0 警告。集成检出的 `prototype/screenshots/`、`prototype-paper/screenshots/` 共登记 62 张 PNG。匿名公开接口按 `changdi-intake/server/README.md` 计 5 个，包含诉求提交、脱敏进度查询及三个停车读取端点。停车接口结果仍为合成数据。

桌面版揭榜书“测试及研发资料”记录 265 项自动化测试、47 张验收截图。本册按集成检出复核结果写 414 例和 62 张，属于更新的工程证据；桌面原件保留其取数时点。数据库 24 张为任务给定快照口径，当前同一集成检出初始化后实测 23 张，待确认差异来自原始检出或统计范围，见第四节。
