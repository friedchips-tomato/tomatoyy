# 04 · 停车推荐、排序与导览侧衔接

---

## 1. 推荐输入与输出契约

**输入**（由导览侧提供）：

| 字段 | 说明 |
| --- | --- |
| `destination_id` | 目的地锚点：点位 id（如 `CD-A01`）或车场 id。必须有明确的「步行起点」坐标/位置 |
| `arrive_at` | 计划到达时刻（带时区）。**由用户或路线表单给出**，无则默认「现在 + 30 分钟」并显式标注为默认假设 |
| `preference` | `save_time`（省总时间）/ `less_walking`（少走路）/ `default`（等权重） |
| `travel_mode` | `drive`（自驾）/ `walk`（步行抵达，不需停车）/ `bike`（骑行抵达） |
| `vehicle` | `{height_m: number\|null, needs_charging: bool, size: "compact"\|"standard"\|"large"}` — 供进出限制筛选用 |

**输出**：`parking_recommendation`（schema 见 02 文档 §2.5），含排序列表、备选、每项的可复算打分明细与人话理由。

**前置条件缺失时的行为**：

- `travel_mode = walk` → 不做停车推荐，直接说明「步行抵达，无需停车」。
- `arrive_at` 缺失 → 用默认到达时刻，理由中写「按到达时刻 30 分钟后估算」。
- 目的地位置缺失 → 无法算步行距离 → **不出推荐**，返回明确的错误原因，不给一个假装算得出的列表。

---

## 2. 候选车场的构成

推荐不只在「已有车场」里排，还要考虑：

- **可达性过滤**：驾车可达性依赖道路数据（现阶段没有）。做法：车场带 `access` 约束（单行、限高、限行时段、封闭时段），按 `arrive_at` 判断是否可进入，不可达 → 排除并在 `excluded` 中说明原因（**排除也要给理由**，不能静默消失）。
- **车场容量与周转**：总车位大的场更可能满足"到达时有位"。
- **步行距离**：从车场到目的地的步行距离与时间。
- **费用**：按 `fee` 结构 + 预计停留时长估算。
- **错峰可行性**：若某场在到达时刻余位不足，是否存在"晚 30/60 分钟到达"的可行方案（这正是错峰建议的来源，也是 `parking_advice_adopted` 的价值来源之一）。

## 3. 排序规则（可解释、可复算）

### 3.1 打分构成

每个候选车场算一个综合分，**分越高越靠前**（固定这个方向，写进 schema 注释）。

```
score = Σ_k  weight_k(preference) × normalized_k × 100
```

| 因子 `k` | 原始值 `raw` | 归一化 `normalized` | 含义 |
| --- | --- | --- | --- |
| `arrive_free` | 到达时刻预计余位（车位） | `min(1, free / need)`，`need = 1`（有位即可）或按车辆数 | 有位最重要 |
| `arrive_free_rate` | 到达时刻空置率 | 已在 [0,1] | 余位充裕度 |
| `walk_cost` | 步行时间（分钟） | `1 - min(1, walk_min / walk_cap)`，`walk_cap` = 15 分钟 | 少走路 |
| `total_time` | 驾车 + 停车 + 步行 估计（分钟） | `1 - min(1, total / total_cap)` | 省总时间 |
| `fee_cost` | 预计费用（元） | `1 - min(1, fee / fee_cap)` | 省钱（权重最低） |
| `confidence` | 预测可信度 ∈ [0,1] | 直接使用 | 来自预测方法与数据新鲜度 |
| `restriction_penalty` | 限制惩罚 ∈ [0,1] | 取负权重 | 单行/限高/限行 |

**归一化上限（cap）必须是显式常量并写进产物**（`artifacts/model.json` 的 `ranking_caps`），否则同一个车场在不同版本下分数不可比，也无法复算历史推荐。

### 3.2 两种偏好的权重

| 因子 | `default` | `save_time`（省总时间） | `less_walking`（少走路） |
| --- | --- | --- | --- |
| `arrive_free` | 0.30 | 0.25 | 0.25 |
| `arrive_free_rate` | 0.15 | 0.10 | 0.10 |
| `walk_cost` | 0.20 | 0.10 | **0.40** |
| `total_time` | 0.20 | **0.35** | 0.10 |
| `fee_cost` | 0.05 | 0.05 | 0.05 |
| `confidence` | 0.10 | 0.15 | 0.10 |

- 权重**归一化到 1.0**，写进产物，可被后台覆盖。
- `confidence` 在两个偏好下都保留，因为"预测不可靠的车场"无论哪种偏好都不该排前面。
- `save_time` 需要真实驾车时间；**没有道路数据时 `total_time` 退化为「步行时间 + 一个固定的驾车常数估计」**，此时权重自动下调并把 `total_time` 归一化改用 walk 近似，且在理由中标注「驾车时间为估算」。**不能假装有路网数据。**

### 3.3 硬性过滤（在打分之前）

以下情形直接排除，不进入打分：

1. 到达时刻该车场**不可进入**（`access` 约束不满足）→ 排除，理由写入 `excluded`。
2. 到达时刻预计余位 = 0 且无错峰方案 → 排除（但推荐其"错峰方案"）。
3. 车辆尺寸/限高不匹配 → 排除。
4. 预测 `unavailable`（D4）→ **不排除，但 `confidence = 0`**，权重实际把它压到末位；理由写「余位暂不可用，仅按步行距离与费用排序」。这样保留了信息（近场仍可能被选）又不假装有预测。

### 3.4 错峰方案

对每个被"余位不足"排除的车场，计算 `+30min` / `+60min` 到达的预测余位；若某档余位 > 0 且总时间增加可接受（增加的分钟数 < 步行节省收益），生成一条错峰建议：

```
{ lot_id, arrive_at: "+30min", arrive_free, extra_minutes, note }
```

错峰建议的采纳入口与普通建议**分开记录**，因为它对应的是另一个价值点（错峰建议采纳率 ≥ 25% 的指标）。

## 4. 人话理由（可读、可复算）

每条理由必须能回溯到 `score_breakdown` 的某一项。**生成规则是确定性的字符串模板**，不是自由文本模型——这样同样输入必得同样输出，运营能复算，测试能断言。

示例（`save_time` 偏好，P1 场景）：

> 1. 到达时预计余位 12 个（约 15% 空置率），有位可停。
> 2. 停车后步行约 2 分钟（150 米），到街区入口很近。
> 3. 预计总时间约 9 分钟（驾车估算 5 分钟 + 步行 2 分钟 + 停车 2 分钟）。
> 4. 费用 5 元/小时，按 2 小时停留估算 10 元。
> 5. 余位数据更新于 3 分钟前，预测可信度较高。
> 6. 注意：1 小时内可能停满，建议先到先停。

生成模板的每一条都对应：
1 ← `arrive_free` + `arrive_free_rate`
2 ← `walk_cost`
3 ← `total_time`
4 ← `fee_cost`
5 ← `confidence`
6 ← 运营文案（来自车场配置 `notes`，可为空则不显示）

**理由必须与分数同源**：如果理由里写了"余位 12 个"，`score_breakdown` 里 `arrive_free.raw` 必须就是 12。写一个"取 score_breakdown 生成理由"的函数，测试断言二者一致。

## 5. 驾车 + 步行 vs 骑行接驳对比

**问题**：车场离目的地远（步行 ≥ 10 分钟）时，可以「驾车到车场 → 骑行/接驳 → 目的地」。

**当前边界（必须写进界面）**：**共享单车/接驳点数据不存在**。因此：

- 数据模型里 `transfer` 字段**保留**：`{mode: "bike"|null, feasible: bool, minutes: number|null, note}`。
- 现阶段 `feasible` 一律 `false`，`note` = "暂无可用接驳点数据"。
- UI 上**不显示**接驳对比按钮（避免展示一个永远说"不可行"的控件），但保留代码路径与数据结构，等真实数据到位再启用。
- 一旦有数据：可行条件为「车场有骑行停放点 且 目的地有取车点 且 骑行时间 < 步行时间」，对比项展示「驾车 6 分钟 + 骑行 4 分钟 vs 驾车 6 分钟 + 步行 12 分钟」。

**不要用"示意骑行"数据来演示**——这正是本项目一贯的边界要求（"不用图上直线充当导航"）。

## 6. 街道与进出限制

**当前真实数据：无。** 只能做到"能表达"：

`parking_lot.access` 结构（02 文档 §2.1）：

```json
{ "open_hours": "06:00-24:00", "one_way": false,
  "restricted_hours": [{ "from": "07:00", "to": "09:00", "note": "潮汐车道：早高峰只出不进" }],
  "height_limit_m": null, "note": "沿江路单行道，需从水埠头方向进入" }
```

处理规则：

- `open_hours` 与 `restricted_hours` 按 `arrive_at` 判断 → 不满足则**排除该车场**并给理由。
- `one_way` / `height_limit_m` / `note` 目前**只展示不判断**（缺少路网），但必须在卡片上把 `note` 显示出来（"沿江路单行道，需从水埠头方向进入"），因为这是真实有用的出行信息。
- `height_limit_m` 可与车辆 `height_m` 比对 → 这一项**可以真正判断**，不需要路网。
- 真实道路数据接入后：把 `access` 扩展为路径级约束（哪条路、单行方向、限行时段、步行可行性），并接入真实驾车时间替换估算值。

### 7.2 停车卡（游客端）的信息层次

```
沿江停车场                        12 / 120 余位
[余位条]
步行 150 米 · 5 元/小时 · 更新于 3 分钟前
预计到达时余位（30 分钟后）12 个 · 空置率 10%   ← 预测，标注来源与时效
[历史实线 → 预测虚线 + 误差区间]
理由：离水埠头最近…
[从这里出发排路线]  [导航过去]
```

要求：

- 预测值必须与"当前余位"**视觉区分**（虚线 + 明确"预计"字样）。
- 数据延迟/过期时显示"数据延迟 X 分钟"/"数据过期，以现场为准"（复用 `ops.js` 现有 `stale` 视觉语义）。
- 预测不可用（D4）时显示"该车场暂无可用余位预测"，**不显示 0**。
- 合成数据来源下，整块区域标注**「模拟数据」**（复用现有 `<span class="tag demo">示范数据</span>` 样式）。

### 7.3 事件衔接

| 事件 | 类型（另一分支已定义） | 触发点 | 状态 |

**边界提醒**：`subjectId` 必须是目录内代码。现有目录只有 `P1`、`P2`（在 `guide-bridge/tourism.js` 与服务端 `CHANGDI_TOURISM_JSON` 两处）。新增车场需要**同步改两处**，属于 `changdi-intake` 侧改动，**超出本任务边界**，需另开任务。

### 7.4 与路线推荐的关系

- 停车推荐是**路线推荐的前置**：自驾模式下，路线起点应由停车推荐给出（"你想停 P1 还是 P2"），再进入现有的三条路线预设选择。
- 本次**不改**路线生成算法（那是另一个任务的领域）；本次只提供"起点候选 + 到达时刻"，并把 `routeDraft` 扩成 `{interests, minutes, mode, start, arriveAt, preference}`。
- 现有 `generateRoutes()` 仍然从 `data.routes` 排序（静态），本次不替换它；但停车推荐的结果会成为 `routeDraft.start` 的来源。

## 8. 明确不做的事

- 不做真实导航（无地图 SDK、无路网数据）。
- 不做真实共享单车/接驳（无数据源）。
- 不做真实驾车时间估算（无路网）——用标注清楚的估算替代。
- 不引入 YOLO/摄像头采集（需许可与硬件，且不是游客端功能）。
- 不改 `changdi-intake` 的任何文件。
- 不新增导览事件类型、不新增车场目录代码。
