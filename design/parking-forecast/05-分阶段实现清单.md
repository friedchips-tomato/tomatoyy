# 05 · 分阶段实现清单

三个阶段按依赖顺序：**设计 → 复杂算法 → 基础 UI**。每阶段给出允许改动的文件、禁止触碰的文件、验收标准与可复算命令。

> **通用约束（三个阶段都适用）**
> - 不提交、不推送、不部署、不执行数据库迁移（本次工作全程只读调研）。
> - 不修改 `changdi-intake/**` 任何文件。
> - 每阶段的产物必须带 `source: synthetic|real` 标记，合成数据一律标注「模拟数据」。
> - 任何"看起来像真实数据"的数字都必须在同屏可见其来源标记。

## 阶段 1 · 设计（Schema + 合成生成器 + 骨架）

**目标**：把"数据长什么样"和"缺数据怎么办"定死，让后面两个阶段不再讨论数据结构。

### 验收标准

| # | 标准 | 怎么验 |
| --- | --- | --- |
| 1.1 | 六份 schema 齐备，所有 record 对象 `additionalProperties: false` | `test_schema.py` 断言：缺字段报错、多字段报错、枚举越界报错 |
| 1.2 | 生成器**完全可复现**：同 seed 同参数两次运行，输出文件逐字节相同 | `test_synth.py`：跑两遍比 sha256 |
| 1.3 | 不同 seed 产出**不同**数据 | 同上，比 sha256 不等 |
| 1.4 | 缺失观测的 `free_spaces` 是 `null` 而非 0 | 断言：生成的 missing 行 `free_spaces is None` 且 `quality == "missing"` |
| 1.5 | 过期观测带 `age_seconds` 且随冻结时长递增 | 断言：`stale` 行 `age_seconds` 单调不减 |
| 1.6 | 注入的 `outage_windows` 区间全部为 missing | 断言逐点检查 |
| 1.7 | `manifest.json` 记录 seed、完整参数、每个文件的 sha256、样本计数 | 断言字段存在且 sha256 与实际文件一致 |
| 1.8 | 数据落在物理合理范围：余位 ∈ [0, total]，空置率 ∈ [0,1] | 全量断言 |
| 1.9 | AR(1) 噪声确实存在自相关（|ρ| > 0.5） | 断言 lag-1 自相关 |

**产出**：`schemas/` + `data/synthetic/` + 生成器。

| 2.2 | 同周期基线的统计窗口右端点 ≤ `issued_at` | 断言 |
| 2.3 | train/valid/test 时间不交叠，且有 ≥24h embargo | 断言 |
| 2.4 | walk-forward 回测每一步只用该步之前的数据 | 断言 |

**B. 降级链**

| # | 标准 | 怎么验 |

| 2.9 | 降级原因写入 `degrade_reason` | 断言 |

**C. 基线与指标**

| # | 标准 | 怎么验 |

| 2.13 | 指标分层：按 horizon / 车场 / 工作日周末 / 天气 / 有无活动 / 数据质量 | `metrics.json` 结构断言 |

| 2.16 | 模型在主口径上**优于最强基线**（合成验收口径），且无某层比基线更差 | 断言 |

**D. 运行时一致性**

| # | 标准 | 怎么验 |
| --- | --- | --- |
| 2.17 | 同一批 500 条输入，Python 与 JS 运行时输出**逐位相等** | `test_consistency.py` + `node:test` |
| 2.18 | JS 运行时能读 `artifact.json` 并校验 schema，不合法则拒绝并降级 | 单测 |

| # | 标准 | 怎么验 |
| --- | --- | --- |
| 2.21 | `score_breakdown` 每项 `contribution` 之和 == `score` | 断言（浮点容差 1e-9） |

| 2.23 | 偏好切换只改权重、不改其他逻辑；两种偏好的排序在构造样例上不同 | 断言 |

| 2.25 | 归一化上限（cap）与权重写进 `artifacts/model.json`，可复算历史推荐 | 断言产物含 `ranking_caps` |

## 阶段 3 · 基础 UI（导览侧接入）

**目标**：让游客端真正用上预测与推荐，并保持"数据真实性标识"的既有纪律。

### 允许改动的文件

```
prototype-paper/data/points.js        # parking 数组新增可选字段（保留旧字段兼容）
prototype-paper/app.js                # 停车卡 / 停车服务页 / 路线表单 / 事件上报
prototype-paper/check.mjs             # 新增停车字段校验
prototype-paper/tests/parking.cjs     # 新增走查脚本（浏览器）
prototype-paper/ops.js                # 运营台车场页（可选）
design/parking-forecast/*.md         # 本目录文档更新（实测结果回填）
docs/方案清单.md                      # 仅更新停车相关条目状态
docs/长堤导览-从样板到上线总清单.md    # 仅更新 5.3/5.4 条目状态与口径声明
```

**仍然禁止**：`changdi-intake/**`、`prototype-paper/data/points.js` 中 `parking` 以外的字段、`prototype/`（像素版原型）。

### 交付内容

1. **停车卡**：当前余位 + 到达时预计余位 + 空置率 + 步行距离/时间 + 费用 + 更新时间 + 预测曲线（历史实线/预测虚线 + 误差区间）+ 数据质量标记（实时/延迟 X 分钟/过期）+ 来源标记（示范/模拟/实测）+ 可复算理由。
2. **停车服务页**：目的地选择（默认路线首站）+ 到达时刻 + 偏好（省总时间/少走路）→ 推荐列表（每项含到达时余位/空置率/步行/费用/更新时间/理由）+ 备选 + 错峰建议。
3. **路线表单扩展**：`routeDraft` 增加 `arriveAt` 与 `preference`；自驾模式下停车推荐结果成为起点候选。
4. **降级在 UI 上的正确表达**：D4 显示"暂无可用余位预测"（不是 0）；过期显示"数据过期，以现场为准"（复用 `ops.js` 现有 stale 视觉）。
5. **事件上报（可选链）**：建议采纳 → `parking_advice_adopted`；导航点击 → `parking_navigation_clicked`（若无真实导航能力，按钮暂不提供，事件类型存在但无触发点时月报按覆盖状态显示，不伪造）。
6. **`check.mjs` 校验**：`lot_id` 合法、fee 结构完整、时间戳可解析、余位 ∈ [0,total]、forecast 长度与粒度一致。

## 未决问题（需要总控或需求方回答）

1. **分母口径**：「MAE ≤ 20%」的分母到底是平均余位、总车位，还是空置率百分点 / WAPE？需求方书面确认前，报告同时给四列（口径 A/B/C/D），但**不能自称达标**。
2. **历史数据**：能否拿到真实车场余位历史？时间跨度、粒度、是否含节假日与活动？拿不到则模型无法验证，只能交付合成验收。
3. **真实数据缺口时长**：需求书里 "20% MAE" 的原始公式是什么（单位是车位的绝对误差怎么变成百分数）？
4. **车场清单与真实属性**：目前只有 P1/P2 两个示范车场，真实的停车场数量、容量、收费、开放时间、限行、单行信息由谁提供？
5. **天气源**：是否允许接入公开天气 API？是否需要申请授权？
6. **活动/事件数据**：街区活动的排期与"对停车需求的拉动强度"由谁给（强度无法从数据反推，只能配置）。
7. **目的地定义**：停车推荐的目的地是"点位 id"还是"街区主入口"？多入口街区需要明确主入口锚点，否则步行距离不可比。
8. **导航能力**：是否接入地图 SDK（高德/腾讯）做「导航过去」？不接则 `parking_navigation_clicked` 无触发点。
9. **运营侧的"错峰采纳率 ≥ 25%"**：分母是推荐曝光数还是全部停车页访问数？口径需书面确认，否则该指标不可算。
10. **Python 依赖**：本机已有 numpy/pandas/sklearn 1.8.0，但**交付物不得假设目标机器已装**——需在阶段 2 结束时给出依赖清单与安装说明（或改写为纯 Python 实现）。
