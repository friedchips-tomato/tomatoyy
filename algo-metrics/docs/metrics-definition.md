# 指标口径定义书（正式测试方案 · 指标部分）

> **文件**：`algo-metrics/docs/metrics-definition.md`
> **版本**：v1.0（2026-11-22） · **归属**：任务 M4 · **契约**：`CONTRACT v1`（含 §4.9 数据库视图契约与 §7 决策记录）
> **配套**：`algo-metrics/docs/data-dictionary.md`（字段级数据字典）、`algo-metrics/registry.py`（机器可读口径）、`algo-metrics/compute.py`（计算函数）

本文件是《乐游蓬江 AI 智慧导览小程序》**正式测试方案里的指标部分**：把需求书给的 10+ 个量化验收指标，
逐条定死「怎么算、分子分母是什么、样本从哪来、边界怎么办、示例长什么样」，
让各算法包能被**同一套脚本**验收，避免出现「同一个 MAE，两边算出来的数不一样」。

### 0.3 通用口径约定（全指标适用）

| 主题 | 约定 |
| --- | --- |
| **时间** | 库内存 UTC ISO8601（带毫秒），**视图输出统一 `+08:00`**（`CONTRACT §4.9`）。本文件所有时间窗、观察窗口、分桶一律**以视图输出的 `+08:00` 为准**。 |
| **坐标** | 基表存 `lat/lon + coord_system(cgcs2000/wgs84/gcj02/bd09)`，视图输出 `latitude/longitude`；**未核坐标留空且 `verified=0`**。任何**涉及距离**的指标，只在**坐标已核验（verified=1）且同一 `coord_system`** 时计算；跨坐标系距离一律留空并标注，不做近似换算。 |
| **数据来源标记** | 每个指标结果必须带 `data_source`（`synthetic` / `real`）与 `verified`（`0/1`）展示位；缺这两个字段的结果**不得进入验收报告**。 |
| **去重** | 比例型指标必须写明去重键（`visitor_id` / `impression_id` / `booking_id`）；**同一实体在分子分母两侧使用同一去重规则**。 |
| **空值** | **缺失 ≠ 0**：缺失的余位、缺失的停留时长一律留空（NULL/空串），**不得用 0 顶替**。 |
| **分母为 0** | 分母为 0 时指标值为 `null`，并在结果里带 `note` 说明原因；**不得用 0、1 或上一周期值顶替**。 |
| **样本量门槛** | 每个指标写明最小样本量；**低于门槛时结论标注"样本不足"**，不判达标。 |
| **分层报告** | 比例/误差型指标必须分层报告（按车场 / 工作日-周末 / 节假日 / 天气 / 时段），**整体一个数字不得单独作为结论**。 |
| **禁止调口径** | 不得为了"指标好看"调整口径或挑选样本（`CONTRACT §5`）。口径变更必须走 §5 变更记录。 |

## 1. 评测框架与本文件的关系

```
registry.py   指标口径的机器可读版本（定义/公式/分子分母/数据来源/目标值/实现入口）
compute.py    通用算子（采纳率/点击率/MAE/MAPE/RMSE/WAPE/命中率/时延/时长/可用率）
adapters.py   把 datasets/ 里的合成评测集接到算子上（本框架自测）
stubs.py      未交付包的桩（value=null, status=not_implemented，不编造数字）
runner.py     执行器：产出 reports/eval-summary.json 与 reports/eval-summary.md
```

**各算法包交付后如何接入**（不互相 import）：

```python
# 在 route-recommender 的评测脚本里
import registry  # from algo-metrics import registry

registry.register_pack_metrics("route-recommender", {
    "route_generation_latency_ms": lambda: {
        "value": 1930.0, "unit": "ms", "n": 100,
        "note": "p50=820ms p95=1930ms max=2410ms，100 点位规模，序列化含在耗时内",
    },
})
```

注册后 `runner.py` 的输出与报告格式不变。

## 2. 逐指标口径

<a id="2-1-路线生成时间"></a>
### 2.1 路线生成时间（≤ 3 秒）

**① 定义**
一次路线推荐请求从进入推荐服务到返回 3 条候选路线的**端到端耗时**。验收看 **p95**（不用平均值），
同时报 p50 与最大值。目标 ≤ 3000 ms。

**② 计算公式**

```
latency_ms = t(响应返回) − t(请求进入)          # 单次请求耗时
指标 = p95(latency_ms)                          # 线性插值分位数
```

- 计时**包含**：候选路线生成、打分、JSON 序列化与响应写出。
- 计时**不包含**：进程启动、模型/索引一次性加载（冷启动首轮单独统计，不计入 p95）。
- 失败/超时请求**不计入时延分位数**，单独统计失败率（失败率 > 1% 时该轮无效）。

**③ 分子分母**
时延类指标无分子分母；**样本量 = 有效请求数 n**（目标 ≥ 100 次）。

**④ 数据来源表与字段**
- `route_result.json`（CONTRACT §4.6）字段 `generated_ms` —— 由 route-recommender 包在自测脚本中采集。
- 路由输入 `route_request.json`（§4.6）用于固定请求集：`duration_minutes=60`、`pace=normal`、
  `transport=walk`、**点位规模 100**（契约基线写明"100 点位规模"）。

**⑤ 样本要求**
≥ 100 次请求（同一请求集重复采样，剔除冷启动首轮）；覆盖 ≥ 3 组不同画像
（历史/美食/亲子兴趣），每组 ≥ 30 次。

**⑥ 边界情况**
- 超时（> 10 s）请求：记为失败，不进 p95，但必须写进报告失败率。
- 空结果（无候选路线）：记为失败。
- 采样期间机器负载需记录（否则 p95 不可复现）。

**⑦ 数值示例**
100 次请求：p50 = 820 ms，**p95 = 1930 ms**，max = 2410 ms → p95 ≤ 3000 ms，**达标**。
（若 p95 = 3400 ms → 未达标，需给优化项而不是改口径。）

**框架对应**：`compute_latency_ms()`；注册表条目 `route_generation_latency_ms`；
本阶段为**桩**（route-recommender 未交付），返回 `value=null`。

<a id="2-2-路线采纳率"></a>
### 2.2 路线采纳率（≥ 40%）

**① 定义**
需求书原文：**「按推荐路线游览并完成的人数 ÷ 获得推荐路线人数」**。

- **主口径（验收用）**：分子 = 按推荐路线**游览并完成**的**人数**（`finish_route`）；
  分母 = **获得推荐路线的人数**（`view_route`）。
- **辅助口径（离线代理）**：曝光明细表上 `adopted=1` 的曝光数 ÷ 曝光总数（人次级），
  只用于算法包自测回归，**不作为对外验收结论**。

> **红线**：分子**不能用点击「出发」（`adopt_route`）的人数替代**（需求书明确要求）。

**② 计算公式**

```
主口径 = |{访客 v : 存在 finish_route(v, r) 且 r ∈ v 看过的路线, 且 ts_finish − ts_view ≤ 24h}|
         ÷ |{访客 v : 存在 view_route(v)}|

辅助口径 = Σ adopted(=1) ÷ Σ 曝光条数        # 按 impression_id 去重
```

**③ 分子分母**
- 分子：**去重访客数**（`visitor_id`），且 `finish_route` 的 `route_id` 必须属于该访客看过的路线。
- 分母：**去重访客数**（`visitor_id`），即"获得推荐路线的人"。
- 观察窗口：**曝光后 24 小时**（跨天完成的算在窗口内，窗口外的剔除并披露数量）。

**④ 数据来源表与字段**
- 视图 `algo_visitor_events`（基表 `visitor_events`，`CONTRACT §4.9`）：
  `visitor_id`、`ts`（+08:00）、`event_type`、`route_id`。
- 事件类型（CONTRACT §4.5 枚举）：`view_route` / `adopt_route` / `finish_route`。
- 离线代理：曝光明细表 `route_impressions_sample.csv`（`impression_id, adopted`）。

**⑤ 样本要求**
主口径 ≥ 300 个"获得推荐"的访客；观察窗口 24 小时；覆盖工作日/周末与节假日。

**⑥ 边界情况**
- 无 `view_route` 的 `finish_route` = 脏数据 → 剔除（并单独计数披露）。
- 同一访客多次曝光 → 只计 1 人（分母去重）。
- 窗口外完成 → 剔除，披露剔除条数。
- 一次会话看完多���推荐路线 → 分子仍只计 1 人（人数口径）；若要按"访客×路线"统计，
  必须另立指标名并显式标注口径，不得与本口径混用。

**⑦ 数值示例**
300 人获得推荐，其中 132 人完成游览 → **132 / 300 = 44.0% ≥ 40%，达标**。
（若 105 人完成 → 35.0%，未达标。）

**框架对应**：`compute_adoption_rate(events, "view_route", "finish_route",
dedup_key="visitor_id", window_minutes=1440, match_field="route_id")`；
注册表条目 `route_adoption_rate`（主）/ `route_adoption_rate_offline`（辅）。

<a id="2-3-语义关联推荐点击率"></a>
### 2.3 语义关联推荐点击率（≥ 25%）

**① 定义**
知识图谱语义关联推荐（故事线 / 关联点位 / 主题卡片）的**曝光 → 点击**转化率。

**② 计算公式**

```
ctr = |{点击曝光}| ÷ |{曝光}|        # 两侧都按 impression_id 去重
```

**③ 分子分母**
- 分子：点击事件数，**按 `impression_id` 去重**（同一曝光 30 分钟内多次点击只算 1 次）。
- 分母：曝光事件数，**按 `impression_id` 去重**（同一推荐位多次渲染只算 1 次曝光）。

**④ 数据来源表与字段**
- 事件流：视图 `algo_visitor_events`（基表 `visitor_events`）。
- 曝光需带 `impression_id`、推荐位 `slot`、推荐实体 `kg_id` 集合、算法版本 `algo_version`。

> **契约待补（TODO，负责人：算法负责人 / 数据库设计指挥）**：
> CONTRACT §4.5 的 `event_type` 枚举里**没有 KG 曝光/点击事件类型**，
> 需要增补 `impress_kg` / `click_kg`（或由 kg 包提供曝光明细表）。
> 在契约增补前，kg-recommend 包可用自有曝光表交付，但**字段名须与本节一致**，否则无法统一验收。

**⑤ 样本要求**
≥ 500 条曝光；覆盖 ≥ 3 个推荐位、≥ 3 个主题；工作日/周末/节假日各有 ≥ 100 条。

**⑥ 边界情况**
- 曝光未渲染完成（用户已滑走 / 首帧外）→ 不计曝光。
- 点击事件必须能关联到 `impression_id`；关联不上的点击**不计入分子**，也不补记为曝光。
- 空结果（无推荐）→ 该次请求**不算曝光**（否则会人为压低 CTR）。
- 重复上报（同一 `impression_id` 多次渲染）→ 只计 1 次。

**⑦ 数值示例**
800 条曝光、216 条点击 → **216 / 800 = 27.0% ≥ 25%，达标**。

**框架对应**：`compute_click_rate(events, "impress_kg", "click_kg", dedup_key="impression_id")`；
注册表条目 `kg_recommendation_ctr`；本阶段为**桩**。

<a id="2-4-语音自然度-mos"></a>
### 2.4 语音自然度 MOS（≥ 3.8 / 5）

**① 定义**
AI 讲解语音的**听感主观评分**（Mean Opinion Score），1–5 分，参考 ITU-T P.808 的 5 级主观听测设计。
MOS 衡量"像不像人说话"，不衡量内容正确性（内容正确性由 §2.5 负责）。

**② 计算公式**

```
单份问卷得分 = mean(3 个题项得分)             # 题目见下
MOS = Σ(单份问卷得分) ÷ 有效问卷数
```

**问卷设计（MOS 问卷）**

| 题号 | 题目 | 量表 |
| --- | --- | --- |
| Q1 | 这段语音听起来自然、不生硬 | 1（完全不像真人）~ 5（完全自然） |
| Q2 | 语速、停顿、语调接近真人讲解 | 1~5 |
| Q3 | 听完全段不别扭、愿意继续听 | 1~5 |

- 每份问卷必须**完整听完**一段（≥ 60 秒）才计分；
- 题项顺序固定（Q1→Q2→Q3），避免顺序效应；
- 每条音频**至少 5 名评分员**，同一评分员**最多计入 3 份问卷**（防疲劳偏差）。

**③ 分子分母**
- 分子：Σ 每份有效问卷的得分（3 题均值）。
- 分母：**有效问卷数**（通过完整性 + 注意力检测的问卷）。

**④ 数据来源表与字段**
- MOS 问卷与评分表（人工听测；表结构：`questionnaire_id, audio_id, rater_id, lang, topic,
  q1, q2, q3, submitted_at, valid, invalid_reason`）。
- 被测音频来源：讲解内容包 `GD*`（CONTRACT §1 ID 规则）。

**⑤ 样本要求**
≥ 30 份有效问卷；覆盖 ≥ 3 个语种（普通话 / 粤语 / 外语）与 ≥ 2 类内容主题；
每条音频 ≥ 5 名评分员。

**⑥ 边界情况**
- 无效问卷（未听完、注意力检测失败、重复提交）→ 剔除，**必须披露无效份数**。
- 同一音频被多人评分时：先按评分员去重（取该音频的中位数分），再参与整体平均。
- 外语内容单独统计，**总体 MOS 必须同时给出分语种结果**（总体达标但某语种显著偏低要列整改项）。

**⑦ 数值示例**
32 份有效问卷，题目均值 Q1=3.86、Q2=3.78、Q3=3.95 → 单份均值后汇总 **MOS = 3.86 ≥ 3.8，达标**。

**框架对应**：注册表条目 `voice_naturalness_mos`；本阶段为**桩**（AI 讲解包后续交付）。
问卷聚合逻辑在 AI 讲解包内实现，聚合口径以本节为准。

<a id="2-5-讲解点位匹配准确率"></a>
### 2.5 讲解点位匹配准确率（≥ 90%）

**① 定义**
AI 讲解在用户所在点位播报的内容，与该点位**实际讲解内容一致**的比例（人工抽检）。

**② 计算公式**

```
accuracy = 匹配正确的讲解条数 ÷ 抽检讲解条数
```

**③ 分子分母**
- 分子：判定为"点位匹配正确"的讲解条数。
- 分母：抽检的讲解条数（一条 = 一次讲解播放）。

**标注集构造（抽检集）**

1. **抽样**：按 `point_id` 分层，每点位抽 ≥ 10 条播放记录（覆盖不同时段与日期），总 ≥ 200 条；
2. **标注**：每条记录标注三项 —— ① 播放时用户所在 `point_id`；② 实际播放的讲解内容 `guide_content_id`
   及其主题；③ 判定结果（`correct` / `wrong_point` / `wrong_content` / `undetermined`）；
3. **复核**：随机抽 20% 由第二位标注员复标，不一致的对齐后再判。

**判定规则**

| 判定 | 条件 |
| --- | --- |
| `correct` | 讲解内容的 `point_id` 与用户所在点位一致 **且** 内容主题与该点位讲解内容一致 |
| `wrong_point` | 播报的是别的点位的内容 |
| `wrong_content` | 点位对但内容与该点位讲解内容不符 |
| `undetermined` | 用户位置不准 / 播放被中断 / 音频缺失 |

`undetermined` **不计入分母**，但必须在报告里单列数量。

**④ 数据来源表与字段**
- 抽检标注表：`play_id, point_id_at_play, guide_content_id, played_at, label, annotator_id`。
- 讲解内容：CONTRACT §4.1 `points.guide_content_id`（`GD*`）。

**⑤ 样本要求**
≥ 200 条抽检讲解，覆盖全部在营点位与 ≥ 3 类内容主题。

**⑥ 边界情况**
- 用户位置不准（GPS 漂移）导致无法判定 → `undetermined`，不计入分母。
- 同一讲解被同一点位多次播放 → 按播放条数计（每条一次机会），但同一用户连续 3 条内只抽 1 条。
- 语音被打断的播放 → `undetermined`。

**⑦ 数值示例**
抽检 220 条：`correct` 205、`wrong_point` 7、`wrong_content` 5、`undetermined` 3
→ **205 / (220 − 3) = 94.5% ≥ 90%，达标**。

**框架对应**：注册表条目 `guide_point_match_accuracy`；本阶段为**桩**。

<a id="2-6-在线预约使用率"></a>
### 2.6 在线预约使用率（≥ 30%）

**① 定义**
**有讲解预约需求的访客**中，最终**成功使用（提交）在线预约**的比例。

**② 计算公式**

```
usage_rate = |{访客: 有 book_guide 事件}| ÷ |{访客: 进入讲解预约入口}|
```

**③ 分子分母**
- 分子：去重访客数，提交了预约（`book_guide` 事件）。
- 分母：去重访客数，**进入讲解预约入口**（预约页曝光）——**不能用"全部游客"当分母**。

**④ 数据来源表与字段**
- 视图 `algo_visitor_events`（基表 `visitor_events`）：`visitor_id`、`ts`、`event_type`。
- 事件类型：`view_booking`（进入预约入口）、`book_guide`（提交预约）。
- 预约单：`bookings` 基表（`booking_id, visitor_id, person_id, status, requested_at, ...`）用于校验。

> **契约待补（TODO，负责人：算法负责人）**：CONTRACT §4.5 的 `event_type` 枚举里
> **没有 `view_booking`（进入预约入口）**，分母事件必须增补，否则该指标无法计算。

**⑤ 样本要求**
≥ 200 个进入预约入口的访客；覆盖工作日/周末与节假日。

**⑥ 边界情况**
- 进入入口但未选讲解员/时段 → **不算使用**（分母里，算分子外）。
- 同一访客重复提交同一单 → 只算 1 人。
- 提交后被系统自动取消（风控）→ 仍算"使用"（口径是提交，不是完成）。
- 进入入口即离开（无任何交互）→ 计入分母（进入就是需求方）。

**⑦ 数值示例**
180 人进入预约入口，57 人提交 → **57 / 180 = 31.7% ≥ 30%，达标**。

**框架对应**：`compute_adoption_rate(events, "view_booking", "book_guide", dedup_key="visitor_id")`；
注册表条目 `booking_usage_rate`；本阶段为**桩**。

<a id="2-7-平均预约确认时长"></a>
### 2.7 平均预约确认时长（≤ 30 分钟）

**① 定义**
从游客**提交预约**到讲解员/客服**确认或明确拒绝**的平均耗时。

**② 计算公式**

```
duration_i = decided_at − requested_at
指标 = mean(duration_i)        # 单位：分钟
```

**③ 分子分母**
- 分子：Σ（有效预约单的 `decided_at − requested_at`）。
- 分母：**有效预约单数**（`status ∈ {confirmed, rejected, completed}`）。

**④ 数据来源表与字段**
- 基表 `bookings`：`requested_at`、`decided_at`、`status`、`cancelled_at`、`completed_at`、
  `slot_id`、`visitor_id`、`person_id`（DB 侧 UTC ISO8601 带毫秒，视图输出 `+08:00`）。
- 基表 `booking_events`：`booking_id, version, action, actor_type, occurred_at, detail`
  —— 用于状态流转留痕与"确认动作发生在哪一刻"的核对。

**⑤ 样本要求**
≥ 100 单有效预约；覆盖工作日/周末/节假日与白天/夜间时段。

**⑥ 边界情况**
- **取消单**（`status=cancelled`）默认**剔除**，另报取消率；口径书里取消单不参与均值。
- `decided_at` 为空的**未决单**不计入分母，但必须在报告里单列"**待确认积压数**"
  （未决单超过 N 单要单独预警，N 取 20）。
- 跨天确认按**真实时间差**计，不做截断。
- `rejected` 计入分母（拒绝了也是"确认了结果"，否则会掩盖响应慢的问题）。
- 时间倒挂（`decided_at < requested_at`）→ 记为脏数据剔除并披露。

**⑦ 数值示例**
120 单有效预约，确认耗时均值 **21.4 分钟** ≤ 30 分钟，**达标**；
取消 9 单（取消率 7.0%，已剔除）、待确认 3 单（单列）。

**框架对应**：`compute_duration_minutes(starts, ends, exclude_cancelled=True)`；
注册表条目 `booking_confirmation_duration_min`；本阶段为**桩**。

<a id="2-8-未来-1-小时车位预测-mae"></a>
### 2.8 未来 1 小时车位预测 MAE（≤ 20%）★ 主口径

> 这是需求书点名要求写清楚的口径：「停车预测的 MAE 需要在正式测试方案中明确单位和计算口径，
> 避免预测指标无法统一验收。」本节按 `CONTRACT §7 决策记录` 的确认结论写死。

#### 2.8.1 预测步长与评估窗口

| 项 | 取值 |
| --- | --- |
| 预测目标 | **未来 1 小时**（horizon = 60 分钟）时刻的**空闲车位数** `free_spaces` |
| 数据粒度 | 契约 §4.3 为 30 分钟或 1 小时；**30 分钟粒度下 = 2 步**（parking-forecast 内部 15 分钟粒度下 = 4 步，取 `by_horizon["60"]`） |
| 评估窗口 | 连续 ≥ 14 天、且覆盖**工作日 / 周末 / 节假日 / ≥ 2 种天气 / 活动日** |
| 最小样本 | ≥ 500 个 `quality='ok'` 的评估桶，且**每车场 ≥ 100 桶** |
| 分层 | 必须按**车场、工作日/周末、节假日、天气、horizon** 分层给出；**整体数字不得单独作为结论** |

#### 2.8.2 ① 定义

预测的空闲车位数与真实空闲车位数的**平均绝对误差**，除以**车位总数**得到无量纲比例。
「≤ 20%」指**这个比例 ≤ 0.20**。

#### 2.8.3 ② 计算公式（主口径 + 两个并列口径）

```
# 【主口径】相对总车位（比例）—— 验收判定用这个
MAE_ratio = mean(|pred_free − actual_free|) / total_spaces
          = Σ|pred_free − actual_free| / Σ total_spaces        # 多车场汇总（按容量加权）

# 【并列口径 1】车位数（个车位）
MAE_spaces = mean(|pred_free − actual_free|)

# 【并列口径 2】空置率（百分点 pp）
MAE_pp = mean(|pred_free/total − actual_free/total|) × 100

# 换算关系
MAE_ratio = MAE_spaces / total_spaces          # 单车场、容量恒定时
MAE_pp = MAE_ratio × 100                        # 仅当每样本容量相同（单车场）时成立
```

**三者分母不同，不可混用**：
`MAE_ratio` 的分母是**车位总数**，`MAE_pp` 的分母是**每样本各自的容量**（先各自归一化再平均），
`MAE_spaces` 不做归一化。多车场且容量不等时，`MAE_ratio ≠ MAE_pp / 100`。

#### 2.8.4 ③ 分子分母

| 口径 | 分子 | 分母 |
| --- | --- | --- |
| **MAE_ratio（主）** | Σ\|预测空闲车位 − 真实空闲车位\|（单位：车位） | Σ `total_spaces`（单位：车位）；单车场时 = 该车场 `total_spaces` |
| MAE_spaces | Σ\|误差\|（单位：车位） | 样本数（得到"平均每个桶差几个车位"） |
| MAE_pp | Σ\|预测空置率 − 真实空置率\|（比例） | 样本数（逐样本先除以本车场容量，再取均值） |

#### 2.8.5 ④ 数据来源表与字段

- 视图 `algo_parking_history`（基表 `parking_observations`）：
  `parking_id`、`ts`（+08:00）、`free_spaces`、`occupied_spaces`、`total_spaces`、
  `quality`（`ok/stale/suspect/missing`）、`age_seconds`、`source`、`evidence`。
- 预测值：parking-forecast 包回测输出的 `predicted_free_spaces`（对应 CONTRACT §4.8
  `parking_forecast.json` 的 `forecast[].predicted_free_spaces`）。
- **空值红线**：`free_spaces` 为 NULL 时 `occupied_spaces` 同样为 NULL，**缺桶按缺口标记、不补零**。

#### 2.8.6 ⑤ 评估样本的**剔除规则**（关键）

| 桶状态 | 是否进主口径 | 处理 |
| --- | --- | --- |
| `quality='ok'` | **进** | 进入分子分母 |
| `quality='missing'`（`free_spaces` 为 NULL） | **不进** | 视为缺桶，**不补零、不插值**；单列**缺失覆盖率** = missing 桶数 ÷ 总桶数 |
| `quality='stale'`（过期，`age_seconds` > 900） | **不进** | 单列**过期覆盖率**；若线上仍在出预测，可另出 stale 桶误差（辅助观察，不进主口径） |
| `quality='suspect'` | **不进** | 同上，单列 |
| `total_spaces` 为 NULL | **不进** | 分母缺失，无法归一化 |

> 即：**MAE 只在 `quality='ok'` 的桶上计算，missing/stale 桶单独统计覆盖率。**
> 同时必须报告"评估桶总数 / 进入计算的桶数 / 被剔除的桶数与原因分布"，
> 避免"只算好桶"变成挑样本。

#### 2.8.7 ⑥ 边界情况

- **分母为 0**：`total_spaces` 缺失或为 0 → 该桶剔除；若全部桶被剔除 → 指标为 `null` 并注明原因。
- **无展示/无预测**：预测缺失（`predicted_free_spaces` 为 NULL）的桶不进分子分母，单列"预测缺失率"。
- **空样本**：评估窗口内没有 `ok` 桶 → 指标 `null`，不得用 0 顶替。
- **多车场汇总**：主口径按**车位容量加权**（`Σ|e| / ΣT`）；同时必须给出**分车场**结果，
  任一车场超阈值即列整改项（整体达标但单场不达标不算通过）。
- **同一车场多次评估**：按桶（lot × ts）去重，同一桶只能算一次。

#### 2.8.8 ⑦ 数值示例（任务书给定例）

```
total_spaces = 100
平均绝对误差 = 8 个车位

MAE_ratio = 8 / 100 = 8%        → ≤ 20%，达标
MAE_spaces = 8                   （个车位）
MAE_pp    = 8                    （个百分点）
```

> ⚠️ 当 `total_spaces = 100` 时，`MAE_ratio × 100` 与 `MAE_pp` **数值相同**，
> 但**分母不同、口径不同**：前者分母是车位总数（比例），后者是逐样本容量归一化（百分点）。
> 车场容量不是 100 时两者**必然不等**，**不可混用、不可互相换算**。

#### 2.8.9 哪个口径进验收报告、哪些做辅助监控

| 口径 | 用途 | 进验收报告 |
| --- | --- | --- |
| **MAE_ratio（主口径）** | 需求书「MAE ≤ 20%」的判定依据 | ✅ **是**（唯一判定口径） |
| MAE_spaces | 运营侧直观理解（"差几个车位"） | ✅ 并列展示（不单独判定） |
| MAE_pp | 与"空置率"直觉对齐 | ✅ 并列展示（不单独判定） |
| WAPE（口径 D）、相对平均余位（口径 A） | 与 parking-forecast 产物对齐、监控分母选择的影响 | ✅ 进**监控附表**，不作为判定口径 |

#### 2.8.10 与 `parking-forecast/artifacts/metrics.json` 的字段对应（读实际产物确认）

`parking-forecast` 阶段 2 产物（`artifacts/metrics.json`，`source=synthetic`）字段口径**实测对应**如下，
字段名**保持不变**，本文件不另起名字：

| 产物字段 | 计算式（读 `parking-forecast/src/pf/backtest.py::compute_metrics` 确认） | 对应本文件口径 |
| --- | --- | --- |
| `mae` | `mean(\|pred_free − actual_free\|)`（车位） | **MAE_spaces**（并列口径 1） |
| `rate_mae_pp` | `mean(\|pred/T − actual/T\|) × 100`（百分点） | **MAE_pp**（并列口径 2）；同时等于产物的 `pct_c` |
| `pct_b` | `mae / mean(total_spaces) × 100`（%） | **MAE_ratio（主口径）×100** |
| `pct_a` | `mae / mean(actual_free) × 100`（%） | 口径 A（相对平均余位），监控用 |
| `pct_c` | `= rate_mae_pp` | = MAE_pp |
| `pct_d` | `wape × 100`（%） | 口径 D（WAPE），监控用 |
| `wape` | `Σ\|e\| / Σ actual_free`（比例） | 口径 D（WAPE） |
| `mape` | `mean(\|e\|/actual)`，**仅 `actual > 0`** | MAPE；配 `mape_excluded_ratio` 披露剔除比例 |
| `mape_excluded_ratio` | 被排除样本占比 | MAPE 剔除比例披露 |
| `rmse` | `sqrt(mean(e²))`（车位） | RMSE |
| `hit_rate` | `P(\|e\| ≤ 1)`（±1 个车位内） | 命中率（阈值 1 个车位） |
| `bias` | `mean(pred − actual)` | 偏差（看系统性高/低估） |
| `denominator.chosen` | 产物当前声明的主百分比口径 | ⚠️ 产物当前写的是 **"wape (口径 D)"**，与本文件**验收主口径 B 不同**，见下方对齐事项 |
| `main_model.by_horizon["60"]` | horizon=60 分钟的分层指标 | **未来 1 小时**对应的分层结果 |
| `main_model.overall_model` | 全 horizon 汇总 | 仅作参考，验收取 60 分钟层 |

> **口径对齐事项（必须在上线阶段闭环，勿回避）**：
> `parking-forecast` 产物报告把 **WAPE（口径 D）** 作为主百分比口径（理由：聚合稳定、不随满位分母趋 0 爆炸），
> 而本口径书按总指挥确认把 **口径 B（相对总车位）** 定为验收主口径。
> 二者**在同一批预测上会给出不同的百分比，甚至跨越 20% 阈值**
> （例：某批预测 `MAE_ratio = 7.9%` 而 `WAPE = 21.3%`）。
> 因此：
> 1. 本文件按确认口径执行，判定用 **口径 B**；
> 2. parking-forecast 的对外报告**必须同时给出口径 B 的数值**（其 `pct_b` 字段已有）；
> 3. **需求方书面确认归一化分母放在上线阶段**——在此之前，任何材料都**不得写"已达标"**，
>    只能写"按约定口径 B 计算为 X%"。

#### 2.8.11 达标判定与本阶段结论

| 层级 | 判定 |
| --- | --- |
| **合成/示例数据（当前阶段）** | 只判定**链路可用**：口径能算、缺桶剔除生效、分层齐全、报告可生成；**数字本身无对外意义**，不判"达标" |
| **正式达标（上线阶段）** | 在**真实历史数据**上：口径 B ≤ 20%，且**每个车场**、工作日/周末、节假日各分层均 ≤ 阈值，并经**现场校验**（人工/闸机抽样对照） |

**框架对应**：`compute_mae(y_true, y_pred, total_spaces)`；
注册表条目 `parking_mae_ratio_1h`（主）/ `parking_mae_spaces_1h` / `parking_mae_pp_1h`（辅）。

<a id="2-9-错峰建议采纳率"></a>
### 2.9 错峰建议采纳率（≥ 25%）

**① 定义**
向访客给出「错峰停车」建议（建议晚到 / 早走以避开高峰）后，实际**采纳该建议**的比例。

**② 计算公式**

```
rate = 采纳次数 ÷ 展示（含错峰建议）次数
```

**③ 分子分母**
- 分子：`adopt_parking` 事件数（访客点击/确认了某条停车建议）。
- 分母：**含错峰建议的停车卡片展示次数**（`view_parking` 事件中带错峰建议的曝光）。

> ⚠️ 分母**不是**"全部停车查询次数"，**不是**"全部曝光"，**只算含错峰建议的曝光**。

**④ 数据来源表与字段**
- 视图 `algo_visitor_events`（基表 `visitor_events`）：`event_type ∈ {view_parking, adopt_parking}`、
  `visitor_id`、`ts`。
- 错峰建议本体：parking-forecast 包的推荐输出（§4.8 `parking_forecast.json` 的错峰理由）。
- **线上需曝光级标记**：曝光事件需要能区分"这条卡片是否带错峰建议"（如 `offpeak_flag=1`
  或推荐位标识）。当前 CONTRACT §4.5 无该字段 → **TODO 契约增补**；
  在增补前，离线代理口径按"该访客本次停车卡片带错峰建议"统计，并在报告中显式声明。

**⑤ 样本要求**
≥ 200 次含错峰建议的展示；覆盖工作日/周末与节假日；至少覆盖 2 个车场。

**⑥ 边界情况**
- 普通余位查询（无错峰建议）→ 不进分母。
- 同一访客对同一张卡片的重复点击 → 只计 1 次。
- 用户自行改选其它车场 → **不计采纳**（采纳的是"错峰"这个建议，不是"停车"这件事）。
- 建议本身不可用（车场满位无法错峰）→ 该次不展示，不进分母。

**⑦ 数值示例**
240 次展示、66 次采纳 → **66 / 240 = 27.5% ≥ 25%，达标**。

**框架对应**：`compute_adoption_rate(events, "view_parking", "adopt_parking", dedup_key=None)`；
注册表条目 `parking_offpeak_adoption_rate`。

<a id="2-10-首屏加载--关键页面响应"></a>
### 2.10 首屏加载 / 关键页面响应（≤ 2 秒 / ≤ 1.5 秒）

**① 定义**
- **首屏加载**：小程序冷启动 → 首页首屏**可交互**（首屏渲染完成 + 首屏关键数据返回）的耗时，目标 ≤ 2000 ms。
- **关键页面响应**：关键页面的**主接口**响应耗时，目标 ≤ 1500 ms。

**② 计算公式**

```
load_ms      = t(首屏可交互) − t(冷启动)
response_ms  = t(接口响应完成) − t(请求发出)
指标 = p95(样本)          # 两者都取 p95
```

**③ 分子分母**
时延类指标无分子分母；**样本量 = 采样次数 n**。

**④ 数据来源表与字段**
- 真机性能采样（冷启动脚本 + 监控上报），字段：`session_id, device_tier, network, page, api,
  started_at, ended_at, duration_ms, cold_start`。
- 关键页面清单：**路线推荐页**（`/route/recommend`）、**停车查询页**（`/parking/forecast`）、
  **讲解播放页**（`/guide/play`）、**预约页**（`/booking/...`）。

**⑤ 样本要求（采样点定义）**
- 每机型档位 ≥ 100 次冷启动；每个关键接口 ≥ 200 次请求。
- **机型档位**（按处理器/内存分档，采样机型须写明具体型号）：

| 档位 | 参考配置 | 说明 |
| --- | --- | --- |
| 高档 | 骁龙 8 系 / A15 以上，RAM ≥ 8 GB | 主力用户机型 |
| 中档 | 骁龙 7 系 / A12–A14，RAM 4–6 GB | 主力覆盖机型 |
| 低档 | 骁龙 6 系 / A11 以下，RAM ≤ 4 GB | 必须覆盖，不得省略 |

- 网络：4G 与 Wi-Fi 各 ≥ 50%。

**⑥ 边界情况**
- **弱网重试**与**二次启动**单独统计，不进主口径（但要在报告里给出）。
- 关键接口只统计**服务端耗时**口径的接口；纯前端渲染耗时不计入响应时间。
- 每个接口**单独判定**；整体 p95 达标但某接口不达标不算通过。
- 必须**按机型档位分列**；高档机达标不能掩盖低档机不达标。

**⑦ 数值示例**
高档机 p95 = 1180 ms、中档 1620 ms、低档 2350 ms → 低档 **超 2000 ms，未达标**，需列整改项
（图片体积、首屏接口串并改并行），**不得改口径或只报高档机**。

**框架对应**：`compute_latency_ms()`；
注册表条目 `first_screen_load_ms`、`page_response_ms_p95`；本阶段为**桩**。

<a id="2-11-核心功能可用率"></a>
### 2.11 核心功能可用率（≥ 99.5%）

**① 定义**
统计周期内，**核心功能请求**中成功完成（非 5xx、非超时、非服务端错误）的比例。

**② 计算公式**

```
availability = 成功请求数 ÷ 核心功能请求总数
```

**③ 分子分母**
- 分子：**成功完成**的核心功能请求数（HTTP 2xx/3xx 且业务返回成功）。
- 分母：**核心功能请求总数**（含失败）。
- **统计周期**：自然周（周一 00:00 – 周日 23:59:59，+08:00）；月报时用自然月再算一遍。

**④ 数据来源表与字段**
- 网关/服务端请求日志：`request_id, api, status_code, latency_ms, error_type, occurred_at, client_id`。
- **核心功能接口清单**（口径固定，不随版本漂移）：路线推荐、停车预测、停车推荐、讲解内容拉取、
  讲解员匹配、预约创建/查询/确认、点位与列表拉取、诉求提交（工单）。

**⑤ 样本要求**
单周期核心功能请求量 ≥ 10000；不足 10000 的周期**不单独判定**（样本不足）。

**⑥ 边界情况**
- **剔除**：客户端主动取消、参数校验失败（4xx）、用户端网络切换造成的中断。
- **计入失败**：5xx、服务端超时（阈值 3 秒）、业务异常抛出。
- **不计入分母**：健康检查、后台管理端请求、静态资源请求。
- 灰度/回滚期间的请求**单独标注**（不与正常周期混算），但必须披露。

**⑦ 数值示例**
一周 128,400 次核心请求、失败 42 次 → **99.967% ≥ 99.5%，达标**；
若失败 700 次 → 99.45%，**未达标**。

**框架对应**：`compute_availability(n_ok, n_total)`（分母为 0 → `value=null` 并带 note）；
注册表条目 `core_availability_rate`；本阶段为**桩**。

## 4. 验收报告模板（字段与展示位固定）

报告由 `runner.py` 自动生成（`reports/eval-summary.json` + `reports/eval-summary.md`），
表格列固定为：**指标名 / 归属包 / 目标值 / 本次结果 / 单位 / 状态 / 样本量 / 口径引用**。

每个指标结果**必须**带下列展示位，缺一不得进报告：

| 展示位 | 含义 |
| --- | --- |
| `data_source` | `synthetic` / `real` —— 数据来源（**本阶段一律 synthetic**） |
| `verified` | 数据是否已核验（合成数据一律 `false`） |
| `n` | 样本量（分母侧） |
| `note` | 口径说明 + 剔除/边界说明（剔除了多少、为什么） |
| `doc_ref` | 指向本文件对应小节 |

**报告首页必须写明三句话**：

1. 口径声明：主口径是什么、分母是什么（MAE 见 §2.8.3）；
2. 数据声明：本结果基于合成/示例数据，**不代表真实业务水平**；
3. 确认状态：**需求方书面确认放在上线阶段**，本阶段按约定口径执行，**不自称达标**。
